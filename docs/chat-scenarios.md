# Системные промпты и сценарии в чате

`POST /api/chat` перед каждым обращением к модели читает активные системные
промпты и сценарии из PostgreSQL. Это работает и при `save_history=false`:
теперь БД требуется для всех запросов чата.

Системные промпты передаются с ролью `system` перед файлами, историей и текущим
вопросом. Порядок: `order_num`, `create_time`, `id`. Изменения через API
применяются со следующего запроса; отключённые записи не передаются.

Пример `POST /api/system_prompt`:

```json
{
  "order_num": 0,
  "prompt": "Отвечай «по этим данным информация отсутствует», если в доступных данных нет ответа. Не выдумывай факты. Доступа к интернету у тебя нет.",
  "is_active": true
}
```

Промпт — инструкция модели; точное соблюдение текста зависит от модели.

## Сценарии

Модель получает все активные сценарии как справочник. Каждый сценарий описывает
таблицу, доступные колонки и алгоритм анализа. Модель вызывает `query_scenario`,
сервер получает данные, возвращает их модели с ролью `tool`, затем модель
формирует ответ. Можно выполнить до 6 вызовов инструментов за запрос.

Нужна модель Ollama с поддержкой [tool calling](https://docs.ollama.com/capabilities/tool-calling).
Вызовы инструментов и промежуточные результаты в историю не сохраняются:
сохраняются сообщение пользователя и конечный ответ.

Пример `POST /api/scenarios` для **уже существующей** таблицы `public.debts`:

```json
{
  "title": "Задолженность",
  "description": "Сумма задолженности по учреждениям организации",
  "table_name": "public.debts",
  "columns_description": {
    "organization": "Код организации",
    "amount": "Задолженность в рублях"
  },
  "scenario": "Для вопроса об общей задолженности запроси SUM по amount. Для разбивки добавь group_by organization. Если SUM вернул null, сообщи, что данных нет. Укажи сумму и валюту; не суммируй усечённую выборку вручную.",
  "is_active": true
}
```

`columns_description` — JSON-объект, ключи которого совпадают с реальными именами
доступных колонок. `table_name` — `table` или `schema.table`. Поддерживаются
обычные и секционированные бизнес-таблицы, без системных таблиц и таблиц самого
приложения. Таблицы бизнеса автоматически не создаются.

Сервер формирует параметризованный SELECT по проверенным аргументам инструмента:
выбор колонок, фильтры, SUM/COUNT/AVG/MIN/MAX и группировка. Произвольный SQL,
JOIN и запись данных не поддерживаются. Сложную формулу можно разобрать на
несколько запросов к сценариям и дальнейший анализ результатов моделью.
Каждая выборка ограничена 200 строками и 5 секундами. Если данные усечены,
инструмент возвращает `truncated=true`; для итогов следует использовать агрегаты.

## Принадлежность данных

В бизнес-таблице обязательна колонка `jurpers`. Сервер всегда добавляет
`jurpers = user_jurpers`. Если передан `user_organization`, добавляется
`organization = user_organization`. Без него выборка включает все организации
внутри заданного `jurpers`, в том числе строки с `organization IS NULL`.
Если нужной колонки нет, инструмент возвращает ошибку вместо расширения выборки.
Модель не может удалить эти условия своими фильтрами.

Пример запроса:

```json
{
  "message": "Какая у меня задолженность по организации?",
  "user_login": "ivan",
  "user_jurpers": 123,
  "user_organization": 42,
  "save_history": false
}
```

`user_organization` — отдельное необязательное поле запроса; значение из
`user_info` не используется как фильтр. `user_jurpers` и `user_organization`
пока поступают из тела запроса. Это фильтрация данных, а не аутентификация:
доверенный вызывающий сервис должен передавать проверенные значения.
Создание чата, список, история, отправка сообщений и удаление используют владельца
из `users` (логин + юрлицо), связанного через `conversations.user_uuid`.

## Проверка

`tests/test_chat_scenarios.py` использует настоящую временную PostgreSQL и
имитацию Ollama. Тесты проверяют передачу промптов, цикл инструментов,
агрегаты, фильтры принадлежности, историю и обработку ошибок.
Запускать только на отдельной тестовой БД: тесты очищают таблицы чатов,
промптов и сценариев. После применения `database/init.sql`:

```bash
TEST_DATABASE=1 PYTHONPATH=app python -m unittest discover -s tests -v
```

Подключение задаётся стандартными переменными `PGHOST`, `PGPORT`, `PGUSER`,
`PGPASSWORD`, `PGDATABASE`.

## Создание чата и файлы

Для диалога с историей сначала вызови `POST /api/chat/create`:

```json
{"user_login": "ivan", "user_jurpers": 123}
```

Необязательное поле `model` закрепляет модель за диалогом; без него выбирается
первая доступная модель Ollama. Ответ `201` содержит `conversation_id`, `model`,
`title`, `created_at`. При создании `title=null`; передавать название не нужно.
Генерация ответа при создании не запускается. После первого успешного сообщения
модель генерирует короткий заголовок по вопросу и ответу. Заголовок сохраняется
и возвращается в поле `title` ответа `/api/chat`. При следующих сообщениях он
не перегенерируется. Этот дополнительный вызов ограничен 15 секундами; при
ошибке основной ответ сохраняется, `title` остаётся null, а следующая отправка
сообщения повторяет попытку по первой паре вопрос–ответ.

Затем загрузи файл через `POST /api/files` (multipart, поле `file`), дождись
ответа с `file_id` и отправь `POST /api/chat`:

```json
{
  "conversation_id": "UUID из ответа создания чата",
  "save_history": true,
  "message": "Что в этом отчёте?",
  "file_ids": ["UUID из ответа загрузки файла"],
  "user_login": "ivan",
  "user_jurpers": 123
}
```

`/api/chat` больше не создаёт диалоги: `save_history=true` без ID возвращает
`422`, неизвестный ID — `404`. Чат без сохранения истории по-прежнему допускает
`save_history=false` без `conversation_id`, в том числе с `file_ids`.

В одном диалоге допускается до 5 файлов. После успешного ответа файл привязан
к чату и передаётся модели при следующих вопросах автоматически. Если модель
вернула ошибку, созданный чат и загруженный файл остаются, но сообщения и новые
привязки откатываются; при повторе передай те же `file_ids`. Несуществующий файл
даёт `404`. Для изображений нужна модель с поддержкой vision.

## Область видимости сценариев

В `POST /api/scenarios` и `PATCH /api/scenarios/{id}` доступно необязательное
поле `visible_jurpers`, например `[123, 456]`. Если поле не передано при
создании или указан пустой список, сценарий доступен всем юрлицам.
В PATCH отсутствие поля сохраняет текущий список, а `[]` снимает ограничение.

Если `user_jurpers` не входит в непустой список, сценарий просто исключается
из контекста модели. Сам запрос чата не завершается ошибкой. Эта область
видимости не отменяет фильтры `jurpers`/`organization` при чтении бизнес-данных.
`GET /api/scenarios?user_jurpers=123` позволяет получить список с таким же
фильтром. Без параметра CRUD API возвращает административный список сценариев.

Схема БД, включая `visible_jurpers`, создаётся через `database/init.sql`
при первой инициализации пустого хранилища PostgreSQL.

## Отчёты и скачивание файлов

`POST /api/reports` создаёт файл XLSX (Excel), CSV или DOCX (Word):

```json
{
  "format": "xlsx",
  "title": "Задолженность по организациям",
  "columns": ["Организация", "Сумма"],
  "rows": [[42, 15000], [43, 20000]]
}
```

Дополнительно можно передать `text` с выводами отчёта. Для текстового DOCX
достаточно `format`, `title`, `text`. Ответ `201` содержит метаданные файла
и `download_url` вида `/api/files/{file_id}/download`. Скачивание выполняется
через существующий `GET /api/files/{file_id}/download`.

Модель получает инструмент `create_report`, даже если нет подходящих
сценариев. При просьбе «выдай отчёт в Excel» она может создать файл и вернуть
ссылку. В JSON ответа `/api/chat` добавлено поле `files` — массив метаданных
готовых файлов с `download_url`, пригодный для кнопок скачивания на фронтенде.
Ссылки также сохраняются в тексте ответа в истории. Исходящие отчёты не
добавляются автоматически к входящим вложениям диалога.

Для отчёта по данным БД модель передаёт `query_result_id`, полученный от
`query_scenario` в текущем запросе. Сервер переносит строки напрямую, сохраняя
фильтры юрлица и организации. Отчёт из усечённой выборки не создаётся:
модель должна уточнить фильтры или запросить агрегаты. Десятичные значения
PostgreSQL переносятся как точные строки без округления через float.

Лимиты прямого API отчётов: 1000 строк, 30 колонок, 1 МБ исходных данных,
5 МБ готового файла. Для данных из сценария дополнительно действует текущий
лимит выборки 200 строк. Если последующий вызов модели завершится ошибкой,
созданные внутри текущего запроса отчёты откатываются вместе с транзакцией.
Файлы не отправляются по почте: интерфейс выдаёт их через ссылки скачивания.


## Список, история и удаление чатов

- `GET /api/chats?user_login=ivan&user_jurpers=123&limit=100&offset=0` — список собственных чатов.
- `POST /api/chat/history` требует `conversation_id`, `user_login`, `user_jurpers` и параметры пагинации.
- `DELETE /api/chat/{id}?user_login=ivan&user_jurpers=123` — удаление чата, сообщений и привязок файлов, ответ `204`.

Чужой/несуществующий чат возвращает `404`. Файлы из общей таблицы `files` не
удаляются: они могут использоваться другими диалогами. Старые записи чатов без
`user_uuid` не становятся автоматически собственностью вызывающего пользователя.
Данные пользователей API получает от доверенного вызывающего сервиса; в APEX
они берутся на сервере из `get_user` и `get_jurpers`, а не из JavaScript.

## Лимит загрузки

`MAX_FILE_BYTES` — переменная окружения API. По умолчанию `5242880` (5 МБ).
Она передаётся из `.env` через Compose. После изменения нужно пересоздать API:
`docker compose up -d api`. `GET /api/files/limits` возвращает `max_file_bytes`,
`max_files` и `extensions`; APEX использует эти значения для интерфейса и
проверки загружаемых частей. Ограничения извлечения текста (3 млн символов),
Excel (1000 строк/100 колонок на лист) и изображений (20 мегапикселей) действуют
отдельно и возвращают понятную ошибку `413`, даже если размер файла допустим.
