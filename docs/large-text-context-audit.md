# Аудит большого текстового файла — 2 октября 2026

## Исходные данные и границы проверки

Файл `qwen_context_stress_test_8000.txt`: 584 804 байта, 399 129 символов,
8 013 физических строк (8 000 записей журнала и вопросы после него).
SHA-256: `30a1097c5b01610679d64ec79de65439ac1e79b3e11cd601df4acbf4a0ec8181`.
Проверен именно исходный файл, а не реконструкция или выборка контрольных строк.

Проверена Ollama `0.34.0` на `192.168.68.56:11434`, модель `qwen3.5:9b`,
Q4_K_M, digest `6488c96fa5faab64bb65cbd30d4289e20e6130ef535a93ef9a49f42eda893ea7`.
`/api/show` сообщает максимальный контекст 262 144, исходный `/api/ps` —
выделенный контекст 50 384. Это разные величины.

Тест сохранения использует отдельную временную PostgreSQL 17: рабочие данные
не изменялись. История и системные сценарии конкретного проблемного чата не
предоставлены; воспроизведение без истории уже показало тот же дефект.

## Где текст сохраняется

1. `upload_file` читает до `MAX_FILE_BYTES + 1`, при превышении отклоняет загрузку.
   Файл меньше 5 МиБ. Для TXT `extract_text` декодирует UTF-8 с удалением BOM
   (при ошибке — CP1251). Никаких срезов по строкам или символам нет.
2. `MAX_TEXT_CHARS = 3000000` ограничивает извлечённый текст; превышение даёт 413,
   а не усечение. Размер исходного файла укладывается в этот лимит.
3. После настоящего INSERT/SELECT в PostgreSQL `content` побайтово равен оригиналу,
   а `extracted_text` посимвольно равен результату декодирования.
4. `file_context` забирает весь `extracted_text`. JSON-экранирование переводов строк
   увеличивает размер представления, но не удаляет текст: обратный разбор даёт
   точное исходное содержимое.
5. Проверен фактический HTTP body через транспорт httpx после `model_messages`
   и `answer_with_scenarios`. Все исходные данные присутствуют полностью.
   Интеграционный тест также проверяет порядок с двумя сообщениями истории.

Запрос без истории с реальными служебными инструкциями API и инструментом отчётов:

| Метрика | Значение |
|---|---:|
| Сумма содержимого messages с разделителями, символы | 410 408 |
| То же, UTF-8 байты | 598 180 |
| Системное сообщение, символы | 3 076 |
| Последнее пользовательское сообщение, символы | 407 330 |
| Описание tools, символы | 1 256 |
| Оценка токенов текста (`UTF-8 bytes / 3`) | 199 394 |
| Точное число токенов от Ollama, включая её шаблон/tools | 240 264 |

Оценка по байтам заметно занижает число токенов данного журнала. Она служит только
диагностикой и не используется для решения «помещается / не помещается».
Точный рендеринг шаблона модели и токенизация происходят внутри Ollama.

Порядок: общий system (активные промпты, сценарии, профиль, правила файлов,
правила инструментов/JSON), затем до 20 предыдущих непустых сообщений, затем
последний user (все прикреплённые файлы + вопрос). История ограничивается числом
сообщений, а не токенами. При вызовах инструментов добавляются assistant/tool.
Диагностика показывает размер каждого сообщения; место под файл уменьшается
на размер инструкций, истории, tools и последующих результатов. Бюджет ответа
также должен помещаться. В данном воспроизведении история равна нулю — её удаление
само по себе проблему этого файла не решает.

Перед HTTP-запросом найдены все маркеры, номера строк и значения:
CONTROL-A/FALCON-731, BETA/91827, CONTROL-B/[3999], CONTROL-C/NEPTUNE-442,
«итоговый множитель»/[7750], 58321/[7999], END-MARKER/[8000].
Проверять только названия маркеров недостаточно: они повторены в вопросах в конце
файла. Поэтому дополнительно проверены значения, номера строк и полное равенство текста.

## Доказанная причина потери

До исправления API не задавал параметр `truncate`; Ollama 0.34.0 по умолчанию
считает его включённым. В `server/prompt.go` сначала удаляются старые сообщения,
с сохранением system и последнего сообщения пользователя. В нашем случае весь файл
находится именно в последнем сообщении; он один превышает доступное окно.

Следующий этап — `llm/llama_server.go`, `completionPromptForRequest`:
если вход не помещается и разрешён context shift, сохраняются `num_keep` начальных
токенов и хвост, а середина удаляется. `contextShiftPromptLimit` оставляет примерно
половину контекста для входа. При `num_keep=4` и `num_ctx=50384` это **25 194 токена**.
Это точно совпало с `prompt_eval_count` в воспроизведении.

Источники для проверенной версии:
- https://github.com/ollama/ollama/blob/v0.34.0/server/routes.go
- https://github.com/ollama/ollama/blob/v0.34.0/server/prompt.go
- https://github.com/ollama/ollama/blob/v0.34.0/llm/llama_server.go

Обычный запрос с файлом и короткой инструкцией имеет 239 069 токенов:

| Режим | Результат |
|---|---|
| `num_ctx=50384`, `truncate=true` | HTTP 200, обработано 25 194 токена; первые четыре значения «не найдены», конец найден |
| `num_ctx=50384`, `truncate=false` | HTTP 400: 239 069 токенов не помещаются в 50 432 (округление окна runner) |
| `num_ctx=262144`, `truncate=false` | HTTP 200, `prompt_eval_count=239069`, `done_reason=stop`; все значения и расчёт верны |

Первое воспроизведение имело `num_predict=512` и завершилось `length`; это отдельное
ограничение выхода, которое не объясняет отсутствие исходных значений. Тест полного
контекста при том же лимите завершился штатно на 340 выходных токенах.

## Исправление

`QwenStrategy._request` всегда передаёт `truncate: false` для chat/generate.
Ни один повтор не включает усечение обратно. При нехватке окна API возвращает
понятную ошибку 422, а не анализ хвоста под видом полного документа.

Глобальный `QWEN_NUM_CTX=50384` сохранён. Полная обработка данного файла проверена
с явным `options.num_ctx=262144`, поддерживаемым именно этой моделью.
Это не универсальный размер для остальных моделей. При дополнительной истории,
сценариях или файлах даже 262 144 может оказаться мало; запрос будет отклонён честно.

Полный прямой тест занял около 281 секунды: обработка входа ~142 секунды,
генерация ~130 секунд. `/api/ps` сообщил ~16,17 ГБ общего объёма загруженной модели
с контекстом и ~8,90 ГБ в GPU. Часть вычислений ушла на CPU. Поэтому увеличение
окна глобально без учёта ресурсов не применено. Для повторного длительного теста
используйте тайм-аут 600 секунд; штатный `QWEN_READ_TIMEOUT=300` близок к времени теста.

## Диагностика в работающем API

Временно включить в `settings.toml`:

```toml
CONTEXT_DIAGNOSTICS = true
```

Список `CONTEXT_DIAGNOSTIC_MARKERS` уже содержит контрольные слова, значения и
номера строк. После обновления кода: `docker compose up -d --build api`.
При дальнейших изменениях только settings: `docker compose restart api`.
Смотреть: `docker compose logs -f api` (записи `context_audit`).

События: `file_extracted`, `file_from_database`, `llm_request`, `llm_http_response`,
`llm_result`. Для запроса выводятся размеры, оценка токенов, `configured_num_ctx`,
порядок и размеры сообщений, наличие маркеров, SHA-256. Для ответа — фактический
`prompt_eval_count`, `eval_count`, `done_reason`. Пары запрос/ответ имеют `audit_id`.
Содержимое документов, base64 изображений, полный ответ и токены доступа не логируются.
Данные images не учитываются в текстовой оценке; это явно указано в записи.
После диагностики вернуть `CONTEXT_DIAGNOSTICS = false`.

## Повторение без изменения БД

Из корня репозитория, стандартным Python (без дополнительных библиотек):

```bash
python scripts/audit_llm_context.py /путь/qwen_context_stress_test_8000.txt \
  --url http://192.168.68.56:11434 --num-ctx 50384

python scripts/audit_llm_context.py /путь/qwen_context_stress_test_8000.txt \
  --url http://192.168.68.56:11434 --num-ctx 262144 --timeout 600
```

Первый вызов должен дать ошибку переполнения, второй — все исходные значения.
`--allow-truncation` служит только воспроизведению старого дефекта, в API такого
переключателя нет. Скрипт передаёт весь указанный файл указанному серверу Ollama.

Для проверки полного Python pipeline — `tests/test_large_file_pipeline.py`:
`TEST_DATABASE=1`, `STRESS_FILE_PATH` — путь к исходному файлу, PG* — реквизиты
**отдельной тестовой БД**. Проверка использует настоящие upload/INSERT/SELECT/
file_context/model_messages/answer_with_scenarios и перехватывает итоговый HTTP body.
Ответ нейросети в этом регрессионном тесте подменён; реальные результаты выше получены
от отдельного обращения к Ollama. Это разные виды проверки.

## Дополнительный результат первого вызова с инструментами

Повторение фактического HTTP body API с `num_ctx=262144` дало
`prompt_eval_count=240264`: все значения присутствуют в ответе модели.
Однако первый ответ оказался вызовом `create_report` без запроса файла,
а в аргументах модель ошибочно написала `5640008` вместо `5555476`.
Это отдельная ошибка выбора инструмента/арифметики, а не утрата контекста.
Этот первый вызов нельзя считать успешным завершением всего чата.
Прямой тест без инструментов выше дал правильный результат.

Для проверки через API после загрузки файла задайте в запросе чата:

```json
{
  "options": {"num_ctx": 262144},
  "think": false
}
```

Это дополнительные поля к обычному ChatRequest, а не полное тело запроса.
Для длительного теста через API может потребоваться временно задать
`QWEN_READ_TIMEOUT = 600` и перезапустить API. Это не увеличивает контекст само по себе.
В APEX отдельного выбора `num_ctx` сейчас нет; глобальную настройку автоматически
не изменяли. Полноценная обработка файлов, превышающих окно, потребует отдельного
механизма разбиения/поиска, который не входит в минимальное исправление усечения.

## Штатный цикл инструментов: обнаруженные соседние ошибки

Дополнительно запущен `answer_with_scenarios` с настоящей Ollama, исходным файлом,
отдельной PostgreSQL и `options.num_ctx=262144`, без подмены ответов модели.
Первый вызов снова увидел все значения, но попытался создать незапрошенный Excel
и передал некорректные аргументы; приложение вернуло ошибку инструмента.
Второй вызов обработал 240 597 токенов и вернул все значения **и правильный
результат 5 555 476**, однако JSON содержал неэкранированные переводы строк.
Приложение запустило предусмотренное исправление формата. Дополнительный длительный
тест был остановлен на этом этапе; успешное завершение всего чата не подтверждено.

Таким образом, потеря входных данных локализована и защищена от молчаливого
продолжения. Отдельно остаются нестабильная арифметика модели, выбор незапрошенного
инструмента и нарушение формата ответа. Увеличение контекста не устраняет эти ошибки.
Не следует считать успешный прямой вызов модели доказательством исправности всего UI.

Регрессионная проверка: общий набор из 67 тестов — 66 успешно, один пропущен
(отсутствующий необязательный старый SQL-файл); затем три теста диагностики/ошибки
переполнения успешно проверены после добавления понятного сообщения пользователю.
Тест полного Python pipeline выполнен с исходным файлом пользователя.
Изменения сделаны в репозитории; работающий API не пересобирался и APEX не менялся.
