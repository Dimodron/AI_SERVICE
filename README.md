# Qween API

Минимальный FastAPI-сервис для Qwen через Ollama.
Код находится в `app/`: `app.py` подключает `routers/router.py` и `routers/file_router.py`;
логика и обработка ошибок находятся в `services/`, модели запросов — в `schemas/`.

## Docker Compose

При первом запуске скопируйте `.env.example` в `.env` и задайте `POSTGRES_PASSWORD`.

```bash
docker compose up --build -d
```

Swagger: http://localhost:8282/docs

Compose запускает API и PostgreSQL; Ollama используется на существующем сервере.
Адрес можно изменить через `QWEN_URL` в `.env` или окружении:

```bash
QWEN_URL=http://192.168.68.56:11434 docker compose up --build -d
```

Остановка: `docker compose down`.

## Хранилище диалогов

PostgreSQL доступен контейнеру API по адресу `postgres:5432`, а с хоста — `127.0.0.1:5432`.
База и пользователь — `qwen` по умолчанию; пароль указан в `.env` (`POSTGRES_PASSWORD`).
Параметры подключения передаются API через `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`.

Таблицы: `conversations` — идентификатор и модель диалога; `messages` — сообщения с ролью и ссылкой на диалог.
Историю диалога следует читать с `ORDER BY id`.
Таблицы создаются из `database/init.sql` при первом запуске на пустом volume.
Данные хранятся в `postgres_data` и сохраняются после `docker compose down`.
Команда `docker compose down -v` удаляет volume вместе с историей.

Запуск только базы и подключение к ней:

```bash
docker compose up -d postgres
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

`/api/generate` работает без истории. `/api/chat` поддерживает оба режима (см. ниже).

Настройка образа: https://hub.docker.com/_/postgres

## Запрос

```bash
curl http://127.0.0.1:8000/api/generate \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Привет!", "model":"qwen3.5:4b"}'
```

Ответ: `{"response":"Ответ модели"}`. Поле `model` необязательно; указанная модель должна быть установлена в Ollama.

Ошибки: 422 — неверный запрос, 502 — ошибка ответа Ollama, 503 — сервер недоступен, 504 — таймаут (300 секунд).

Протокол Ollama: https://docs.ollama.com/api/generate

`GET /api/models` загружает актуальный список моделей из Ollama (`GET /api/tags`)
по адресу `QWEN_URL` и возвращает массив имён, например `["qwen3:14b", "qwen3.5:4b"]`.
Список запрашивается также перед генерацией и чатом. Новые модели доступны сразу после
добавления в Ollama, без изменения кода и перезапуска API.

Передавайте имя модели в поле `model`. Если оно не указано, используется первая модель
из списка Ollama; порядок списка может меняться.
Для существующего диалога используется сохранённая модель.
Отсутствующая модель возвращает 422. Если список пуст и модель не указана, возвращается 503.
В `/api/generate` и `/api/chat` доступны необязательные параметры:

- `think`: `true` / `false` либо уровень `low`, `medium`, `high`, `max` для поддерживающих его моделей.
- `options.num_ctx`: положительное целое число — размер контекста в токенах, влияющий на расход памяти.
- `keep_alive`: длительность хранения модели в памяти, например `"5m"`, либо число секунд; `0` выгружает после запроса, `-1` оставляет загруженной.

Без параметров (или при `null`) `think` и `num_ctx` определяются настройками Ollama,
а `keep_alive` остаётся `"30m"`. Настройки действуют на текущий запрос и не сохраняются в диалоге.
Поддержка режима рассуждений зависит от модели. API возвращает конечный ответ без текста рассуждений.

Пример запроса к `/api/chat`:

```json
{
  "message": "Привет",
  "model": "qwen3.5:4b",
  "think": false,
  "options": {"num_ctx": 8192},
  "keep_alive": "5m"
}
```

Для `/api/generate` замените `message` на `prompt`.

## Чат с историей и без

После обновления: `docker compose up --build -d`.

`POST /api/chat`, без истории и без файлов (по умолчанию, база не используется):

```json
{"message": "Привет", "save_history": false, "model": "qwen3.5:4b"}
```

Новый диалог с сохранением:

```json
{"message": "Меня зовут Иван", "save_history": true, "model": "qwen3.5:4b"}
```

Ответ: `{"conversation_id":"UUID", "model":"qwen3.5:4b", "response":"Привет, Иван!"}`.
В режиме без истории `conversation_id` равен `null`.

Продолжение — подставьте UUID из ответа:

```json
{"message": "Как меня зовут?", "save_history": true, "conversation_id": "UUID"}
```

Для сохранения истории сначала создайте диалог через `/api/chat/create`.
Модель можно сменить через `PATCH /api/chat/{conversation_id}/model`; неизвестный UUID — 404.
Если в `/api/chat` явно передана модель, отличающаяся от текущей модели диалога, ответ — 409.
`conversation_id` вместе с `save_history: false` возвращает 422.

Все сообщения сохраняются в PostgreSQL. В модель передаются последние 20 сообщений и текущий запрос;
длинная переписка также ограничивается контекстом выбранной модели. Старые сообщения не удаляются из базы.
При ошибке генерации запись отменяется. Одновременные запросы одного диалога выполняются последовательно.
Для локального запуска с историей нужны переменные `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`;
в Compose они уже настроены. API пока не имеет авторизации: доступ к диалогу определяется его UUID.

Протокол чата Ollama: https://docs.ollama.com/api/chat

Интеграционные тесты (используют PostgreSQL из `PG*`, ответы Ollama подменяются):

```bash
PYTHONPATH=app pipenv run python -m unittest discover -s tests -v
```

## Прикрепление файлов

Оригинал файла (`BYTEA`), извлечённый текст и метаданные хранятся в PostgreSQL, в таблице `files`.
Таблица `conversation_files` связывает файлы с диалогами. Отдельного файлового хранилища нет;
для сохранности файлов достаточно сохранять volume PostgreSQL и резервные копии базы.

Все таблицы описаны в `database/init.sql` с `IF NOT EXISTS`. При обновлении существующей базы:

```bash
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < database/init.sql
docker compose up --build -d
```

1. Загрузите файл через `POST /api/files` (`multipart/form-data`, поле `file`).
   В Swagger появится кнопка выбора файла.

```bash
curl http://localhost:8282/api/files -F 'file=@expenses.xlsx'
```

Ответ содержит `file_id`, `filename`, `media_type`, `size_bytes`, `created_at`.
Метаданные доступны по `GET /api/files/{file_id}`, оригинал — `GET /api/files/{file_id}/download`.

2. Передайте `file_id` в чат:

```json
{
  "message": "Проанализируй динамику затрат в файле",
  "save_history": true,
  "file_ids": ["UUID из ответа загрузки"],
  "model": "qwen3.5:4b"
}
```

При продолжении сохранённого диалога достаточно `conversation_id`: прикреплённые файлы подставляются автоматически.
Новый файл можно добавить через `file_ids` в следующем сообщении. Повторная передача того же ID не создаёт дубликатов.
При ошибке модели новая привязка откатывается вместе с сообщениями; сам загруженный файл остаётся в базе.

При `save_history: false` файлы используются только в текущем запросе и не привязываются к диалогу,
но загрузка файлов всё равно сохраняет их в PostgreSQL. Без файлов и без истории чат не обращается к базе.

Поддерживаются TXT и CSV в UTF-8 или Windows-1251, а также XLSX, PNG и JPEG (.jpg/.jpeg). Старый XLS, PDF, DOCX, GIF и WebP пока не поддерживаются.
Лимиты первой версии: 5 МБ на файл, 12000 символов извлечённого текста суммарно на запрос/диалог,
до 5 файлов на диалог; Excel — до 1000 строк и 100 колонок на лист, распакованный размер до 20 МБ.
При превышении лимитов API возвращает 413, а не обрезает данные. Ограничение контекста модели остаётся в силе.
Формулы Excel передаются текстом, не вычисляются; отдельного механизма точных табличных расчётов пока нет.
Файлы не удаляются автоматически. Как и диалоги, они пока доступны по UUID без авторизации.

## Соединения и диагностика

API использует общий HTTP-клиент Ollama и пул PostgreSQL: до `PG_POOL_SIZE` соединений на процесс
(по умолчанию 10), ожидание свободного соединения — до 10 секунд, очередь — до 50 запросов.
Пул создаёт подключения по необходимости: запуск API и чат без истории/файлов не требуют доступной БД.
Соединения закрываются при остановке приложения. При перегрузке хранилища API возвращает 503.

Транзакция сохранённого диалога удерживается до ответа модели, чтобы параллельные сообщения не смешивались,
а ошибка генерации не оставляла частичную историю. Размер пула ограничивает число таких операций одновременно.

`GET /health` проверяет только процесс API; Docker использует его для healthcheck.
Ошибки зависимостей логируются по типу без содержимого сообщений и файлов.
`main.py` также можно запустить напрямую: `pipenv run python app/main.py` (порт 8282).

Если при сборке Docker возникает ошибка DNS внутри контейнера, для Linux можно собрать с сетью хоста:

```bash
docker build --network host -t queenapi-api .
docker compose up -d --no-build --wait
```


## Изображения

Изображения загружаются через тот же `POST /api/files`. Оригинал сохраняется в `files.content` (`BYTEA`);
поле `extracted_text` остаётся пустым. Изменения схемы БД не нужны.

```bash
curl http://localhost:8282/api/files -F 'file=@photo.png'
```

Полученный `file_id` передайте в чат:

```json
{
  "message": "Что изображено на картинке?",
  "file_ids": ["UUID изображения"],
  "model": "qwen3.5:4b",
  "save_history": true
}
```

Можно смешивать изображения и документы в `file_ids`. Изображения передаются в Ollama через `messages[].images`
в base64, без OCR. В сохранённом диалоге они доступны при следующих запросах по `conversation_id`.
При `save_history: false` вложения используются только для текущего запроса.

Проверяются настоящий формат и целостность изображения. Лимиты по умолчанию (меняются в `settings.toml`): 5 МБ и 20 мегапикселей на изображение,
до 5 вложений суммарно на диалог. Анимированный PNG не поддерживается. Лимит текста не учитывает изображения,
но изображения занимают контекст модели.
Перед отправкой изображений API проверяет `vision` через `/api/show`; отсутствующая модель или отсутствие
поддержки изображений возвращает 422 с пояснением, без сохранения неудачного сообщения.
При последней проверке сервера `qwen3.5:4b` и `qwen3.5:9b` поддерживали изображения;
теги `qwen3.5:latest` и `qwen3.5:14b` отсутствовали.

Протокол: https://docs.ollama.com/capabilities/vision

## Копирование бизнес-таблиц Oracle → PostgreSQL

`POST /api/dublicate` загружает таблицы для сценариев из Oracle, указанной в настройках сервера.
Задайте в `.env` `ORACLE_HOST`, `ORACLE_PORT` (1521), `ORACLE_USER`, `ORACLE_PASS`,
`ORACLE_NAME` (service name), `ORACLE_SCHEMA` (APXWS), `DATA_IMPORT_TOKEN` (секретный токен).
Пользователю Oracle достаточно доступа SELECT к исходным таблицам.
`DATA_IMPORT_TIMEOUT` в `settings.toml` — общий таймаут в секундах, по умолчанию 600.
После настройки: `docker compose up -d --build api`.

```bash
curl -X POST 'http://127.0.0.1:8282/api/dublicate?table=DEBTS,PAYMENTS&mode=replace' \
  -H "X-Import-Token: $DATA_IMPORT_TOKEN"

curl -X POST 'http://127.0.0.1:8282/api/dublicate?table=DEBTS&version=2026&mode=append' \
  -H "X-Import-Token: $DATA_IMPORT_TOKEN"
```

Токен в примере должен быть экспортирован в окружение shell. Не передавайте его в URL.
Без настроенного токена маршрут возвращает 503, с неверным — 403.

Параметры передаются в query string:

- `table`: от 1 до 20 имён таблиц через запятую; схема берётся из ORACLE_SCHEMA.
- `filter` и `values`: имена колонок и соответствующие строковые значения через запятую;
  условия равенства объединяются через AND. Значения передавайте с URL-кодированием.
  Запятые внутри одного значения и SQL-выражения не поддерживаются.
- `version`: сокращение для `filter=version&values=...`; не сочетается с filter/values.
- `mode=replace` (по умолчанию): пересоздать таблицу и загрузить выбранные строки.
  При фильтре остальные строки прежней копии удаляются.
- `mode=append`: заменить только строки выбранного фильтра, остальные сохранить.
  **Без фильтра заменяются все строки**, как в исходном примере. Это не добавление дублей.
  Несовпадение структуры существующей копии возвращает 409, нужен replace.

Имена приводятся к нижнему регистру, копии находятся в отдельной схеме `oracle_data`.
В сценарии укажите `table_name: "oracle_data.debts"` и опишите разрешённые колонки в
`columns_description`. Для выборки данных пользователя требуется колонка `jurpers` или `jur_pers`,
при выборе организации — `organization`. Названия колонок сохраняются, кроме регистра:
если в Oracle колонка называется иначе, создайте представление с нужными псевдонимами
и импортируйте его. Импорт сам не создаёт сценарии и не меняет область их видимости.

Ответ содержит режим, список таблиц, количество скопированных строк и типы колонок.
Все таблицы одного запроса обновляются одной транзакцией PostgreSQL; ошибка загрузки
откатывает изменения. Oracle читается в режиме READ ONLY. Данные передаются порциями
по 1000 строк; больших файлов выгрузки на сервере не создаётся.
Копируются данные и базовые типы, но не индексы, связи, триггеры и ограничения Oracle.
Объектные типы, пространственные данные и интервалы не поддерживаются (422).
Имена должны состоять из латинских букв, цифр и `_`, начинаться с буквы, длина до 63.

Драйвер работает в [асинхронном Thin-режиме python-oracledb](https://python-oracledb.readthedocs.io/en/stable/user_guide/asyncio.html).
Для старых Oracle, требующих Thick-режим, понадобится отдельная адаптация подключения.


## Общие настройки

Все общие лимиты и параметры сервисов собраны в корневом `settings.toml`.
Например:

```toml
MAX_FILE_BYTES = 5242880  # 5 МиБ на файл
MAX_FILES = 5            # вложений суммарно на чат
MAX_TEXT_CHARS = 3000000 # извлечённого текста на файл и суммарно на чат
```

Там же настраиваются размеры изображений, ограничения Excel, адрес и таймауты Ollama,
таймаут генерации заголовка, пул PostgreSQL, число вызовов инструментов нейросети,
размер результата сценария и таймаут импорта Oracle. Пароли, логины, токены и реквизиты
подключения PostgreSQL/Oracle остаются в `.env`.

При первом обновлении выполните `docker compose up -d --build api`.
После этого файл подключён в контейнер напрямую: для применения изменений достаточно
`docker compose restart api`. Настройки читаются при запуске; неверные значения,
неизвестные ключи и неположительные лимиты вызывают ошибку запуска с указанием проблемы.
Для запуска без Docker используется тот же файл в корне проекта; другой путь можно
задать переменной `SETTINGS_FILE`.

Для совместимости непустые переменные окружения `MAX_FILE_BYTES`, `MAX_FILES`,
`PG_POOL_SIZE`, `QWEN_URL`, `DATA_IMPORT_TIMEOUT` имеют приоритет над файлом.
**Удалите эти строки из старого `.env`, если хотите управлять ими только через
`settings.toml`, затем один раз выполните `docker compose up -d --force-recreate api`.**

`GET /api/files/limits`, проверка ChatRequest, сервис вложений и сообщения об ошибках
используют одни значения. Oracle/APEX получает лимиты через этот маршрут: после перезапуска
API обновите страницу чата, переустанавливать процедуры для изменения лимитов не требуется.


## Профиль пользователя, администратор и вложения чата

В `settings.toml` задаётся `USER_CONTEXT_TABLE = "oracle_data.gpt_user_context"`.
Это копия вашей Oracle view, импортируемая обычным `/api/dublicate`.
Поиск выполняется по точному `login` (одна строка на логин). Ожидаемые необязательные
колонки: `full_name`, `position`, `jurpers`, `jurpers_name`, `organization`,
`organization_name`, `institution`, `institution_name`. Другие поля модели не передаются.
Отсутствующая таблица или профиль не блокируют чат. При нескольких строках на логин
профиль игнорируется с записью в журнал. Выбранные `user_jurpers`/`user_organization`
приходят из доверенного Oracle-контекста; профиль не переопределяет эти значения.
Профиль сохраняет названия юрлица, организации и учреждения независимо от текущего выбора.
Названия выбранного юрлица/организации заполняются из профиля только при совпадении ID;
профиль не переопределяет область доступа к бизнес-данным.
Пустой `USER_CONTEXT_TABLE` отключает загрузку профиля.

Флаг `users.is_admin` по умолчанию false, отдельно от импортируемого профиля:

```sql
UPDATE users SET is_admin = TRUE WHERE login = 'admin_login';
```

Администратор определяется сервером по login. Для включения его привилегий настройте
одинаковый секрет `CHAT_API_TOKEN` в `.env` API и `c_chat_token` в пакете Oracle `GPT_API`.
Пакет отправляет `X-Chat-Token` и получает login из сессии Oracle, а не из браузера.
При заданном токене запросы ко всем маршрутам группы чата (включая models и chats)
без него отклоняются. Без настроенного токена права администратора не включаются.
Это аутентификация серверного клиента: передавать его токен в браузер нельзя.

Администратор видит все активные сценарии; инструмент чтения не добавляет обязательные
фильтры jurpers/organization, но применяет явно указанные фильтры сценарного запроса.
Обычные пользователи сохраняют прежние ограничения. Служебные таблицы недоступны
инструменту и для администратора, доступ к чужим личным чатам не расширяется.
`ADMIN_IGNORE_SYSTEM_PROMPTS = true` отключает для администратора только промпты из
таблицы `system_prompt`; технические правила работы с файлами и инструментами остаются.
Для сравнения анализа с обычными промптами можно поставить false и перезапустить API.
Результат инструмента содержит источник и фактические фильтры; администратору модель
получает указание объяснять использованные данные и расчёты, а не придумывать результаты.

`POST /api/chat/{conversation_id}/files` принимает `user_login`, `user_jurpers`, `file_ids`:
проверяет владельца, сохраняет вложения без вопроса и не вызывает нейросеть.
Повторное сохранение тех же file_id не создаёт дополнительные сообщения.
`POST /api/chat/history` возвращает `files` у каждого сообщения и общий список вложений
диалога. Файл и вопрос сохраняются одной транзакцией после успешного ответа модели.
Все входящие файлы диалога повторно передаются модели при следующем вопросе, после
истории и перед текущим вопросом. Доступный объём анализа по-прежнему ограничен контекстом
выбранной модели; наличие файла в истории не гарантирует, что модель осмыслит любой объём.

На существующей БД примените `database/init.sql` через psql с `ON_ERROR_STOP=1` перед
обновлением API: добавятся `is_admin` и `message_files`, сброс данных не требуется.
Порядок обновления Oracle описан в `oracle_serv/README.md`.


## Сеть внешнего контейнера Ollama

API подключён к внешней сети `queen-ai` и к своей сети `default` для PostgreSQL.
Перед первым запуском создайте сеть: `docker network create queen-ai`
(если она уже существует, повторять не нужно). Подключите внешний контейнер:
`docker network connect --alias ollama queen-ai ollama`. При `QWEN_URL=http://ollama:11434`
оба контейнера должны находиться в этой сети. API подключается автоматически через
compose.yaml после пересоздания. Для сохранения подключения Ollama при её пересоздании
добавьте внешнюю сеть queen-ai также в Compose/настройки запуска самой Ollama.
Документация: https://docs.docker.com/compose/how-tos/networking/

Фильтры импорта сопоставляются с колонками Oracle без учёта регистра, затем SQL использует
точное имя из метаданных. Поддерживаются как `LOGIN`, так и quoted-колонка `"login"`.
Если имя фильтра отсутствует или имена колонок неоднозначны после приведения к нижнему
регистру, импорт возвращает 422 и сохраняет прежнюю копию.


## Названия выбранного юрлица и организации

В `settings.toml`:

```toml
JURPERS_DIRECTORY_TABLE = "oracle_data.zv_gpt_jurpers"
ORGANIZATION_DIRECTORY_TABLE = "oracle_data.zv_gpt_organizations"
```

Первый справочник содержит `jurpers`, `jurpers_name`; второй — `organization`,
`organization_name`, `jurpers`. При каждом вопросе API ищет текущее юрлицо по
`user_jurpers`, организацию — одновременно по `user_organization` и `user_jurpers`.
Организация из другого юрлица не используется. `user_organization = 0` нормализуется
в отсутствие выбора (`null`), поиск организации и обязательный фильтр по ней пропускаются.
Профиль по login остаётся отдельным: личное юрлицо не заменяет текущий выбор.
Если справочника, колонки или записи нет, название неизвестно и чат продолжает работу.
При нескольких совпадениях название из справочника не используется. Пустая строка в
настройке отключает соответствующий справочник. Название юрлица можно взять из профиля
только при совпадении ID. Название организации берётся из профиля только при отключённом
справочнике и совпадении обоих ID. Справочники не расширяют права доступа и не меняют
владельца чата. В Oracle всё ещё нужно реализовать `GPT_API.organization()` для передачи
текущего выбора организации; отсутствие выбора допустимо.


## Переключение модели в существующем чате

`PATCH /api/chat/{conversation_id}/model` принимает `user_login`, `user_jurpers`, `model`.
Проверяются владелец, наличие модели в Ollama и поддержка изображений, если они уже
сохранены в чате. При ошибке прежняя модель остаётся. Обновляется только модель диалога:
история, заголовок, файлы и последнее время сообщения сохраняются.
Переключение и отправка вопроса используют блокировку одного диалога, чтобы не менять
модель посередине обработки сообщения. Следующие вопросы используют сохранённую модель.
История API дополнительно возвращает актуальное поле `model` для повторного открытия чата.
Это не перенос внутренней памяти модели: новой модели передаются сохранённые последние
20 сообщений, текущий вопрос и вложения, как и при обычном запросе. Модели могут отличаться
поддержкой инструментов, изображений и размером контекста.


## Владелец чата и область бизнес-данных

Владелец чата определяется только по login. Переключение выбранного юрлица не скрывает
собственные чаты и не меняет их владельца. Это применяется к списку, истории, сообщениям,
вложениям, смене модели и удалению. Старые записи users с одним login и разными jurpers
сохраняются; их чаты доступны этому логину, новых записей на каждое юрлицо не создаётся.
Колонка users.jurpers оставлена для совместимости со старыми данными, для проверки
владельца не используется. Сброс или перенос данных не требуется.

В ChatRequest user_jurpers остаётся обязательным текущим контекстом из Oracle/APEX.
У обычного пользователя сервер добавляет условие по этой величине к бизнес-запросам
независимо от значений профиля и users. Поддерживаются колонки jurpers и jur_pers;
если есть обе, используется jurpers. У администратора обязательного ограничения нет.
Для явного отбора администратором добавьте фактическое имя колонки (например jur_pers)
в columns_description сценария. Не используйте выдуманное имя jurpers_id.
В операциях, которым нужен только владелец, user_jurpers теперь необязателен;
старый Oracle-клиент может продолжать его передавать.

Выбор модели в APEX доступен только при `ZGET_ROLE() = 0`. Для остальных
пользователей список скрыт; Oracle-процедуры не принимают выбор модели при создании
и запрещают её переключение. В API проверки этой роли нет.
Модель для новых чатов без явного выбора задаётся в `settings.toml`:
`DEFAULT_MODEL = "qwen3.5:9b"`. После изменения перезапустите API.
Существующие чаты сохраняют свою модель. `GET /api/models/config` возвращает
`default_model`; роль и видимость списка определяет APEX.

Поля `create_user` и `edit_user` в API промптов и сценариев принимают и возвращают
логин, например `"create_user": "ZVEREV"`. Пользователь должен существовать в `users`;
неизвестный логин возвращает 422. Поля необязательны, допускается `null`.
Внутренние UUID и внешние ключи БД сохранены; существующие записи не требуют
конвертации. ID самого сценария, промпта и диалога остаётся UUID.
